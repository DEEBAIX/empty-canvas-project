# استعادة النسخة وتشغيل DATAHub مستقلاً على الـ VPS

## النتيجة المطلوبة
تشغيل `data.tg-kw.com` بالكامل على الـ VPS، بما يشمل التطبيق وقاعدة البيانات وتسجيل الدخول وواجهة البيانات، ثم استعادة ملف النسخة المرفوع دون الاعتماد على Lovable Cloud في الإنتاج.

## ما تم التحقق منه
- ملف `.backup` صالح وهو **PostgreSQL Custom Dump** كامل، أنشئ بواسطة `pg_dump 18.4` ويحتوي على 636 عنصراً.
- ملف `.zip` لا يحتوي شيئاً إضافياً؛ هو فقط نفس ملف `.backup` مضغوط، لذلك سنستخدم `.backup` مباشرة.
- النسخة تشمل جداول التطبيق وبياناتها، ومنها `countries`, `datasets`, `leads`, `api_keys`, `user_roles`، وتشمل أيضاً مستخدمي المصادقة في `auth.users`.
- التطبيق الحالي لا يقرأ `DATABASE_URL` إطلاقاً؛ بل يتصل بخدمات قاعدة البيانات والمصادقة عبر عنوان ومفتاح API. لذلك استعادة الملف في PostgreSQL عادي وحدها لا تجعل التطبيق يستخدمه.
- الصفحة الرئيسية نفسها لا تجلب بيانات، لذا استعادة قاعدة البيانات وحدها ليست علاجاً مؤكداً لخطأ 500. السبب الفعلي يحتاج سجل PM2؛ وبما أن السجل غير متاح الآن، سيبدأ التنفيذ بفحص آلي للبناء والمتغيرات والمسار والخدمة.

## الخطة

### 1. سكربت إنقاذ ونشر واحد
تحديث `deploy-all.sh` ليصبح الأمر الوحيد المطلوب على الخادم، ويقبل مسار النسخة:

```text
bash deploy-all.sh /root/0e42e42f-136c-40df-9ff7-ff7c87340d77_260817.backup
```

السكربت سيكون قابلاً لإعادة التشغيل بأمان، ويتولى:
- فحص Ubuntu والذاكرة والمساحة وملف النسخة قبل أي تغيير.
- تثبيت Docker Compose والأدوات اللازمة فقط عند غيابها.
- إنشاء كلمات ومفاتيح قوية على الخادم وحفظها في ملف محمي بصلاحية `600`، دون طباعتها في السجل.
- أخذ نسخة احتياطية من قاعدة VPS الحالية إن كانت موجودة قبل الاستبدال.
- التوقف برسالة واضحة عند أي فشل، بدلاً من إكمال نشر ناقص.

### 2. تشغيل Backend متوافق محلياً
تشغيل حزمة خدمات محلية عبر Docker Compose تشمل:
- PostgreSQL.
- خدمة تسجيل الدخول والجلسات.
- Data API التي يعتمد عليها كود التطبيق الحالي.
- API gateway داخلي مربوط على `127.0.0.1` فقط.

سيبقى المستخدم الحالي حساب الأدمن، ولن نضيف جدول `profiles` لأن المنصة تحتاج حساب أدمن ودوراً منفصلاً فقط.

### 3. استعادة ملف الـ backup بطريقة آمنة
- التحقق من قائمة محتويات النسخة قبل الاستعادة.
- استخدام عميل PostgreSQL 18 لقراءة صيغة النسخة، حتى لو كان خادم قاعدة البيانات بإصدار أقدم متوافق.
- استعادة مخططات المصادقة و`public` والبيانات والتسلسلات والدوال والسياسات بالترتيب المناسب، مع تجاهل ملاك Lovable Cloud والأدوار الداخلية غير الموجودة محلياً.
- عدم تنفيذ `pg_restore` الخام على قاعدة مستخدمة؛ الاستعادة تتم في قاعدة جديدة مؤقتة، ثم تُجرى اختبارات سلامة قبل اعتمادها.
- التحقق بعد الاستعادة من أعداد المستخدمين والأدوار والدول والمجموعات والليدز، ومن تطابق التسلسلات مع أعلى IDs.
- توضيح أن ملف قاعدة البيانات يستعيد metadata الخاصة بالتخزين، لكنه لا يحتوي بالضرورة على ملفات Storage الثنائية نفسها.

### 4. توجيه التطبيق إلى الخدمات المحلية
- جعل متغيرات العميل والخادم تشير إلى `https://data.tg-kw.com` مع مفاتيح البيئة المحلية الجديدة.
- ضبط عنوان الموقع وروابط تأكيد تسجيل الدخول للمجال نفسه.
- إعادة بناء التطبيق بعد كتابة متغيرات العميل، ثم تشغيل مخرج Node الصحيح عبر PM2.
- إبقاء Lovable Preview على Lovable Cloud للتطوير، بينما نسخة VPS تستخدم البيئة المحلية فقط.

### 5. إصلاح Nginx وخطأ 500
تعديل Nginx بحيث:
- مسارات `/auth/v1`, `/rest/v1`, `/storage/v1` وخدمات backend المطلوبة تذهب إلى الـ API gateway المحلي.
- بقية المسارات تذهب إلى تطبيق Node على المنفذ 3010.
- الخدمات الداخلية لا تكون مكشوفة مباشرة للإنترنت.

ثم ينفذ السكربت اختبارات فعلية:
1. فحص قاعدة البيانات والخدمات المحلية.
2. فحص endpoint المصادقة وData API.
3. فحص تطبيق Node مباشرة على `127.0.0.1:3010`.
4. فحص `https://data.tg-kw.com/` عبر Nginx.
5. عند أي 500: طباعة آخر سجل مناسب من PM2 والخدمة التي فشلت، مع بقاء النسخة السابقة قابلة للرجوع.

### 6. تحديث دليل التشغيل
تحديث `DEPLOY.md` بأوامر قصيرة فقط:
- رفع ملف `.backup` إلى `/root/`.
- تشغيل السكربت الواحد.
- التحقق من أعداد السجلات وتسجيل الدخول.
- `redeploy` للتحديثات اللاحقة دون إعادة استيراد النسخة.
- أمر rollback وأوامر التشخيص عند الحاجة.

## ضوابط الأمان والاستعادة
- لا توضع كلمات قاعدة البيانات أو مفاتيح الخدمة أو GitHub token داخل Git أو داخل أوامر ظاهرة.
- لا يُفتح منفذ PostgreSQL أو API gateway للعامة.
- لا تُحذف قاعدة سابقة قبل نجاح قاعدة مؤقتة واختبارات الصحة.
- لا يُعاد استيراد النسخة تلقائياً مع كل `redeploy`؛ الاستيراد عملية أولية منفصلة داخل نفس السكربت عند تمرير مسار الملف فقط.

## معيار النجاح
- الصفحة الرئيسية تعيد HTTP 200 ولا تعرض شاشة `This page didn't load`.
- يمكن تسجيل الدخول بالحساب المستعاد والوصول إلى لوحة التحكم.
- أعداد `leads`, `datasets`, `countries`, و`user_roles` بعد الاستعادة مطابقة للنسخة.
- إنشاء/قراءة البيانات ومفتاح API يعملان من خدمات الـ VPS فقط.
- إيقاف اتصال VPS بخدمات Lovable Cloud لا يعطل نسخة الإنتاج.
